# STAGE 10 — PUBLIC WEB DASHBOARD

**Goal:** a live, public URL anyone can open with no login, showing the same five views as the Power BI file.
**Estimated time:** 4–6 hours
**Inputs:** `data/dashboard/*` (the committed aggregates — never the full dataset)
**Outputs:** `app/streamlit_app.py`, a live URL, `docs/screenshots/web_*.png`

---

## 10.1 Why this stage exists

Power BI Service requires a work or school account. A gmail address cannot create one,
so the `.pbix` cannot be published to a public link. The `.pbix` stays in the repo as
evidence of BI-tool capability (and it is the artefact an audit employer recognises);
this stage adds the clickable demo that a recruiter can open from a phone.

## 10.2 Platform decision

**Primary: Streamlit Community Cloud.**

| Criterion | Streamlit Community Cloud | Vercel (static export) |
|---|---|---|
| Cost | Free | Free |
| Deploys from | A public GitHub repo, directly | A public GitHub repo |
| Language | Python — reuses `src/` | JavaScript/HTML; charts rewritten |
| Interactivity | Full (filters recompute server-side) | Client-side only |
| Cold start | Sleeps after ~7 days idle; wakes in ~30 s | Instant, never sleeps |
| URL | `<app>.streamlit.app` | `<project>.vercel.app` |
| Effort | Low | Medium |

**Decision (pre-registered): build Streamlit first and deploy it.** If time allows, add
the static fallback described in §10.7 and host it on GitHub Pages or Vercel, and link
both from the README. Streamlit is the right primary because it reuses the Python work
and because recomputing Benford per filter selection is the whole point of the
interaction.

> Vercel cannot host a Streamlit app (it is a long-running Python server, not a
> serverless function). If the agent wants Vercel specifically, the deliverable there
> must be the static export of §10.7, not the Streamlit app. Do not attempt to force
> Streamlit onto Vercel.

## 10.3 Data contract for the app

The app **must not** read anything from `data/processed/`. It reads only from
`data/dashboard/`, which is committed and capped at 25 MB. This keeps the repo clean,
the app fast, and the deploy reproducible.

```python
@st.cache_data
def load_dashboard_data() -> dict:
    """Loads the nine files from data/dashboard/ into a dict of DataFrames/dicts.
    Paths resolved relative to the repo root so it works locally and on the cloud.
    Raises a clear Streamlit error box if a file is missing, naming the file and

```

If `top_risk_5000.csv` proves too large once other files are added, reduce it to the top
2,000 rows rather than exceeding the cap. Log the decision.

## 10.4 App structure — five tabs mirroring the Power BI pages

```python
# app/streamlit_app.py

st.set_page_config(page_title="Audit Analytics — Transaction Anomaly Detection",
                   page_icon="🔍", layout="wide")

# --- Header ---
#   Title, one-paragraph framing (the audit engagement scenario, condensed),
#   an explicit banner: "Demonstration project. Anomalies were synthetically
#   injected into a real public dataset so detection accuracy could be measured."
#   Links: GitHub repo · methodology · PDF workpaper

tabs = st.tabs(["Overview", "Benford's Law", "Anomaly Explorer",
                "Model Performance", "Segment Heatmap"])
```

### Tab 1 — Overview
- 5 metric tiles via `st.metric`: total transactions, total value, aggregate MAD (+ verdict as the delta text), % high risk, anomalies detected in the top 500.
- Line chart: monthly volume with a second series for % flagged.
- Bar: top 10 countries by value.
- Donut or bar: risk band distribution.
- A short "What this shows" expander written in plain English.

### Tab 2 — Benford's Law
- Two select boxes: **Country** (incl. "All") and **Month** (incl. "All").
- Grouped bar: observed vs expected leading-digit %, redrawn from
  `benford_by_segment_digit.csv` for the chosen segment.
- Three tiles: n, MAD, verdict — verdict tile colour-coded to the Nigrini bands.
- The chi-square value with the excess-power caveat printed directly beneath it.
- A sorted horizontal bar of MAD by segment with the four threshold bands shaded.
- A note explaining, in two sentences, what the digit test is and why deviation matters.

### Tab 3 — Anomaly Explorer
- A **review budget** slider (10 → 2,000) — the app shows: how many transactions that
  is, what share of injected anomalies fall inside it, and the precision at that k.
  This single control communicates the whole value proposition.
- The ranked table (`top_risk_5000.csv`), filterable by risk band, country, month and
  by each rule flag.
- Row selection → a detail panel showing every flag, its reason string, the composite
  score breakdown (a small stacked bar: IF / rules / Benford contributions), and the
  `suggested_procedure`.
- A download button for the top-50 review list as CSV.

### Tab 4 — Model Performance
- Metric tiles: AP (with its 95% CI), precision, recall, F1 at the operating point.
- PR curve with the baseline line drawn in.
- Precision@k curve (log x).
- The method × anomaly-type heatmap — rendered from `method_comparison.csv`.
- The caveats list rendered verbatim from `model_metrics.json`, not retyped.

### Tab 5 — Segment Heatmap
- Country × month matrix coloured by % flagged, with a toggle to switch the colour
  metric to MAD.
- A table of the flagged segments below it.

## 10.5 Charting

Use **Plotly** (`plotly.express` / `graph_objects`) rather than matplotlib in the app —
hover tooltips and zoom make an enormous difference to how a dashboard feels, and
`st.plotly_chart(fig, use_container_width=True)` is one line. Add `plotly>=5.20` to
`app/requirements.txt`.

Chart rules for the app (same spirit as `src/viz.py`):
- One consistent palette, defined once at the top of the file; red reserved for risk.
- Every axis labelled with units; percentages formatted as percentages.
- Titles state the conclusion, not the mechanic.
- No chart without a one-line caption explaining what to look for.

## 10.6 Deployment — exact steps

1. `app/requirements.txt`:
   ```
   streamlit>=1.33
   pandas>=2.1
   numpy>=1.26
   plotly>=5.20
   pyarrow>=15
   ```
   Keep it minimal — do **not** reuse the root `requirements.txt`; scikit-learn,
   openpyxl and jupyter are not needed at runtime and slow the build.
2. `app/.streamlit/config.toml`:
   ```toml
   [theme]
   primaryColor = "#1F4E79"
   backgroundColor = "#FFFFFF"
   secondaryBackgroundColor = "#F4F6F8"
   textColor = "#1F1F1F"
   font = "sans serif"
   ```
3. Test locally: `streamlit run app/streamlit_app.py` — every tab must render with no
   exception and no `FileNotFoundError`.
4. Push to GitHub (the repo must be **public**).
5. Go to `https://share.streamlit.io`, sign in with GitHub, **New app**, select the
   repo, branch `main`, main file path `app/streamlit_app.py`, deploy.
6. Wait for the build; check the logs if it fails (most common causes: a missing file in
   `data/dashboard/`, a package absent from `app/requirements.txt`, or a path built with
   `..` that resolves differently on the cloud — always resolve paths from the repo root
   via `Path(__file__).resolve().parents[1]`).
7. Copy the public URL into the README badge and into `docs/resume_and_interview.md`.
8. Open the URL in a private browser window on a phone to confirm it works with no login.

## 11.1 Notebook rules (restated, because this is where the rule gets broken)

Notebooks are **written last** and contain **no logic**. Each cell is one of:
markdown narration · an import · a call into `src/` · a display or plot.

| Notebook | Narrates | Calls |
|---|---|---|

## 12.1 Document structure

**Header block (every page):** engagement name, "Prepared by / Date / Reviewed by",
workpaper reference (e.g. `AA-BEN-01`), page x of y. This framing alone signals audit
literacy.

**Page 1 — Executive summary**
- Objective (one paragraph)
- Scope: population, period, value, what was excluded and why (cancellations, adjustments)
- Summary of procedures performed (the three layers, one line each)
- **Summary of findings**: a 4–6 row table of the conclusions
- Conclusion paragraph — carefully worded: *"Analytical procedures identified N
  transactions (x% of the population, £y) exhibiting characteristics warranting
  further enquiry. These results are indicators for targeted testing and do not, of
  themselves, evidence misstatement or fraud."*

**Page 2 — Scope, data and limitations**
- Population reconciliation table (the cleaning ledger)
- Data reliability commentary
- The synthetic-anomaly disclosure, stated up front and plainly
- Limitations list

**Page 3 — Digit-distribution analysis (Benford)**
- Method and threshold source (Nigrini)
- Aggregate result: the observed-vs-expected chart, MAD, verdict
- The excess-power note
- Segment results: the MAD-by-segment chart plus a table of flagged segments
- Finding statement, with the specific digit driving each flagged segment

**Page 4 — Rule-based exception testing**
- The five tests with their audit rationale, thresholds applied, and exception counts
- The threshold-ratio table as a control observation
- The period-end concentration chart and the outlier months

**Page 5 — Statistical outlier analysis and combined results**
- Isolation Forest in two sentences of plain English (no jargon: *"an unsupervised
  algorithm that scores how easily a transaction can be separated from the rest of the
  population"*)
- Validation results and what they mean for reliance
- The method × anomaly-type matrix with its interpretation
- The recall-vs-effort chart framed as: *"reviewing the top 500 items surfaces x% of
  known anomalies, against y% expected from random selection"*

**Page 6 — Schedule of items for review**
- The top 25 transactions: rank, txn id, date, customer, country, amount, risk score,
  signals fired, suggested procedure
- A sign-off block: Prepared by / Date / Reviewed by / Date

## 12.2 Tone rules (these matter more than the formatting)

| Never write | Write instead |
|---|---|
| "the model detected fraud" | "the procedure identified items exhibiting characteristics associated with…" |
| "suspicious transactions" | "items warranting further enquiry" |
| "the AI found" | "the analysis identified" |
| "proves" | "indicates" / "is consistent with" |
| "99% accurate" | "precision of x% at the selected threshold, on a synthetic validation set" |

Every finding follows the audit structure: **Criteria · Condition · Cause (if known) ·
Effect · Recommendation.** Even where cause is unknown, say so — "cause not determined;
further enquiry recommended" is a professional sentence.

## 12.3 Production

Two acceptable routes:
1. **reportlab** — `src/workpaper.py` builds the PDF programmatically (platypus:
   `SimpleDocTemplate`, `Table`, `Paragraph`, `Image`), pulling every number from
   `reports/metrics/` so the document regenerates when the pipeline reruns. **Preferred**
   — it makes the workpaper reproducible, which is itself an audit virtue.
2. The `pdf` skill route, if the agent has it available.

Do not hand-write the PDF in a word processor; it will drift from the numbers.

Typography: a serif body face at 10 pt, 1.15 line spacing, generous margins, tables with
hairline rules and no fill except header rows, figures at 90 mm wide with numbered
captions ("Figure 3 — Leading-digit distribution, United Kingdom, September 2011").
